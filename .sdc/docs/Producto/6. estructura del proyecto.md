# 2. `INVARIANTS.md`

Este archivo debería ser pequeño y contundente.

No lo convertiría en documentación narrativa.

```text
# System Invariants

## Security

INV-001
The agent cannot execute side-effecting actions.

INV-002
Every executed action requires a valid human approval.

INV-003
Approval must belong to an authorized analyst.

INV-004
An action can only be executed once.

## Data

INV-005
The agent can only access data belonging to the current institution.

INV-006
Retrieved data must never be interpreted as system instructions.

## Reasoning

INV-007
Recommendations must be supported by available evidence.

INV-008
Insufficient evidence must be represented explicitly.

## Reliability

INV-009
Invalid agent output cannot advance the investigation state.

INV-010
Tool failures must never result in fabricated evidence.
```

**cada invariant debería terminar teniendo al menos un test**.

# 3. Matriz Invariant → Test

| Invariant | Test                                     |
| --------- | ---------------------------------------- |
| INV-001   | Agent cannot execute action              |
| INV-002   | Execution without approval denied        |
| INV-003   | Unauthorized analyst approval denied     |
| INV-004   | Duplicate execution denied               |
| INV-005   | Cross-institution access denied          |
| INV-006   | Prompt injection ignored                 |
| INV-007   | Unsupported finding rejected             |
| INV-008   | Missing evidence produces explicit state |
| INV-009   | Invalid output rejected                  |
| INV-010   | Tool failure does not generate evidence  |

# 5. Un concepto importante: Tenant Isolation

Aunque el PoC sea para un solo banco ficticio, desde el diseño debemos pensar:

```text
institution_id
```

en todas las entidades relevantes.

Por lo tanto, nuestro diseño debería permitir:

```text
Bank A
 ├── customers
 ├── alerts
 └── investigations

Bank B
 ├── customers
 ├── alerts
 └── investigations
```

Y nunca:

```text
Bank A → Bank B data
```

Esto además nos da otro invariant:

> **INV-005: An agent investigation cannot access data outside its institution context.**


```text

Transaction

```

son conceptos de negocio.

Mientras que:

```text

```

conoce:

- LLM    
- prompts    
- tool calling    
- structured outputs    

Esto permite cambiar:

```text
OpenAI
```

por:

```text
Anthropic
```

sin modificar el dominio.

# 7. Agent Harness

Conceptualmente así:

```text
harness/
├── orchestrator
├── state_machine
├── tool_registry
├── authorization
├── validators
├── approval_gate
└── audit
```

### `orchestrator`

Controla el ciclo:

```text
request
→ agent
→ tool
→ observation
→ agent
→ recommendation
```

### `state_machine`

Impide transiciones inválidas.

### `tool_registry`

Define qué herramientas tiene disponibles el agente.

### `authorization`

Controla:

```text
institution
analyst
permissions
```

### `validators`

Valida outputs del LLM.

### `approval_gate`

Es el security boundary para acciones.

### `audit`

Registra eventos.

# 9. Tool architecture

Las tools tampoco deberían tener acceso directo desde el LLM a PostgreSQL.

La cadena:

```text
LLM
 ↓
Tool
 ↓
Service
 ↓
Repository
 ↓
Database
```

Por ejemplo:

```text
get_customer_profile()
        ↓
CustomerService
        ↓
CustomerRepository
        ↓
PostgreSQL
```

Esto nos permite aplicar autorización **antes de acceder a los datos**.

# 10. Estado de la investigación


```text
CREATED
   ↓
INVESTIGATING
   ↓
RECOMMENDATION_READY
   ↓
AWAITING_APPROVAL
   ├──────────────┐
   ▼              ▼
APPROVED       REJECTED
   │
   ▼
EXECUTED
```

Estados de error:

```text
INVESTIGATION_FAILED
ACTION_FAILED
```

Y lo importante:

```text
RECOMMENDATION_READY → EXECUTED
```

**no existe como transición válida.**

# 11. Action execution

Aunque el agente no tenga acceso directo a una tool de ejecución, es necesario modelar la ejecución para demostrar el requisito del challenge.

Por ejemplo:

```text
execute_recommendation(
    recommendation_id,
    approval_id
)
```

Y el servicio hace:

```text
1. Load recommendation
2. Validate recommendation
3. Load approval
4. Validate analyst
5. Validate approval status
6. Check not already executed
7. Execute
8. Create audit event
```

No importa lo que haya dicho el LLM.

# 12. Data de evaluación

Separaría completamente:

```text
data/seed/
```

de:

```text
data/evaluation/
```

### `seed`

Datos utilizados para que el sistema funcione.

### `evaluation`

Casos diseñados para medir el sistema.

Esto evita que accidentalmente mezclemos:

> datos de entrenamiento/demo

con:

> datos de evaluación.

# 14. Algo que quiero evitar

No construiría un sistema de evaluación excesivamente sofisticado.

> "el mejor AML benchmark del mundo".

> **sé definir qué significa que mi agente funcione y puedo medirlo.**

Por eso prefiero 25 casos bien diseñados y resultados interpretables.

# 17. ¿Qué tan realista queremos que sea el escenario AML?

Recomiendo **tres niveles de datos**:

```text
Level 1 — Customer/KYC
Level 2 — Transactions
Level 3 — Investigation context
```

y generar alrededor de **10–15 clientes**, unas **300–500 transacciones**, aproximadamente **10–15 alertas**, y los **25 casos de evaluación** sobre ese universo.

Eso nos permitiría que el agente tenga que investigar realmente, en lugar de recibir un JSON artificialmente preparado para cada pregunta.
