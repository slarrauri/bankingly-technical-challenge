# 1. Principio arquitectónico

> **El LLM decide qué investigar y qué recomendar; el sistema determina qué está permitido hacer.**

```text
                    ┌──────────────────────┐
                    │       Analyst        │
                    └──────────┬───────────┘
                               │
                         Investigate
                               │
                               ▼
                    ┌──────────────────────┐
                    │    Agent Harness     │
                    │                      │
                    │ Auth / Authorization │
                    │ State                │
                    │ Tool permissions     │
                    │ Validation           │
                    │ Approval             │
                    │ Audit                │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │      LLM Agent       │
                    │                      │
                    │ Planning             │
                    │ Tool selection       │
                    │ Reasoning            │
                    │ Recommendation       │
                    └──────────┬───────────┘
                               │
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
       Customer Tool    Transaction Tool    Policy Tool
             │                 │                 │
             └─────────────────┼─────────────────┘
                               ▼
                         Data Layer
```

> **El LLM no debe hablar directamente con la base de datos**.

# 2. Las cinco capas

## Layer 1 — Presentation

Para el PoC puede ser extremadamente sencilla.

Responsabilidad:

- seleccionar alerta    
- iniciar investigación    
- mostrar findings    
- mostrar evidencia    
- mostrar recomendación    
- aprobar/rechazar    
- mostrar resultado    

No necesitamos una UI sofisticada.
Hacer una interfaz web mínima.

---

# 3. Layer 2 — Agent Harness

Esta es la capa más importante.

Responsabilidades:

### Identity

¿Quién está haciendo la solicitud?

```text
analyst_id
institution_id
```

### Authorization

¿Ese usuario puede investigar esa alerta?

### Tool permissions

¿Qué tools puede utilizar el agente?

### State management

¿Cuál es el estado actual de la investigación?

### Validation

¿La respuesta del LLM cumple el schema esperado?

### Action control

¿La acción propuesta está permitida?

### Human approval

¿Existe aprobación válida?

### Audit

¿Qué ocurrió y quién lo hizo?

---

# 4. Layer 3 — Agent

Acá vive el LLM.

Su responsabilidad es **razonar dentro del espacio de acciones que le damos**.

Por ejemplo:

```text
Input:
AML-00127

Available tools:
- get_alert
- get_customer_profile
- get_transactions
- get_transaction_summary
- get_previous_alerts
- get_aml_policies
```

El agente podría decidir:

```text
1. Get alert
2. Get customer profile
3. Get transaction summary
4. Get detailed transactions
5. Get AML policies
6. Analyze evidence
7. Produce recommendation
```

No:

```text
prompt → LLM → answer
```

Si:

```text
goal
 ↓
reason
 ↓
tool
 ↓
observe
 ↓
reason
 ↓
tool
 ↓
observe
 ↓
recommend
```

# 5. Layer 4 — Tools

Las tools son el contrato entre el agente y el mundo externo.

El LLM **no debe conocer cómo está implementado PostgreSQL**.

Sólo conoce:

```text

```

Por detrás tenemos:

```text
Tool
 ↓
Service
 ↓
Repository
 ↓
PostgreSQL
```

# 7. Flujo completo

### Step 1 — Analyst selects alert

```text
AML-00127
```

### Step 2 — Harness creates investigation

```text
status = INVESTIGATING
```

### Step 3 — Agent receives objective

```text
Investigate AML alert AML-00127
and provide a recommendation.
```

### Step 4 — Agent calls tools

Por ejemplo:

```text
get_alert()
get_customer_profile()
get_transaction_summary()
get_transactions()
get_previous_alerts()
get_aml_policies()
```

### Step 5 — Agent builds investigation

Produce:

```text
Findings
Evidence
Risk indicators
Missing information
Applicable policies
Recommendation
Confidence
```

### Step 6 — Harness validates output

No aceptamos cualquier texto.
Tenemos un schema estructurado.

Por ejemplo:

```text
{
  recommendation,
  rationale,
  evidence,
  missing_information,
  applicable_policies
}
```

### Step 7 — Recommendation stored

```text
status = AWAITING_APPROVAL
```

### Step 8 — Analyst reviews

El analista puede:

```text
Approve
Reject
Request more investigation
```

### Step 9 — Harness validates approval

Si:

```text
approval == valid
```

se permite la acción.

Si no:

```text
ActionRejected
```

# 8. El punto crítico: Structured Output

No quiero que el agente devuelva:

> "Creo que sería conveniente escalar esta alerta porque..."

como único output.

Se requiere algo estructurado:

```text
Recommendation:
ESCALATE_ALERT

Risk assessment:
HIGH

Confidence:
0.84

Findings:
- Transaction volume increased significantly.
- Multiple new counterparties appeared.
- Activity is partially inconsistent with historical behavior.

Missing information:
- Supporting documentation for recent consulting income.

Applicable policies:
- P-001
- P-002
- P-003
```

Esto permite:

- validar    
- almacenar    
- evaluar    
- auditar    
- renderizar    
- cambiar de proveedor LLM

# 9. Schema validation

Acá entra Pydantic utilizando Python.

Conceptualmente:

```text
LLM
 ↓
Structured output
 ↓
Pydantic validation
 ↓
Valid?
 ├── No → retry / reject
 └── Yes
       ↓
Harness
```

Esto permite demostrar:

> **El prompt solicita una estructura; el código la valida.**

# 10. Approval Gate

Supongamos que el LLM produce:

```text
recommendation = CLOSE_ALERT
```

Eso **no significa**:

```text
action = CLOSE_ALERT
```

Son cosas diferentes.

Tenemos:

```text
Recommendation
      ↓
Human Approval
      ↓
Action Authorization
      ↓
Execution
```

Incluso podríamos diseñarlo así:

```text
Recommendation {
    id
    investigation_id
    action
    rationale
    created_at
}

Approval {
    recommendation_id
    analyst_id
    decision
    timestamp
}

Action {
    recommendation_id
    executed_by
    executed_at
}
```

Y la ejecución sólo acepta una recommendation que tenga un Approval válido.

# 11. Security boundary

### Untrusted

Todo output proveniente del LLM.

### Trusted

El código del Harness.

Esto es muy importante porque el LLM debe ser tratado como un componente probabilístico, no como una autoridad.

```text
             UNTRUSTED
        ┌─────────────────┐
        │       LLM       │
        └────────┬────────┘
                 │
                 ▼
        ┌─────────────────┐
        │     Harness     │
        │     TRUSTED     │
        └────────┬────────┘
                 │
                 ▼
          Side-effecting
             systems
```

# 12. ¿Dónde ponemos las políticas?

Tenemos dos tipos de políticas.

### Business / AML policies

Por ejemplo:

> Rapid movement of funds requires enhanced review.

Estas pueden ser consultadas por el agente.

### System safety policies

Por ejemplo:

> Closing an alert requires human approval.

Estas **no deberían depender del LLM**.

Las implementamos en código.

> **Las políticas de negocio ayudan al modelo a razonar; las políticas de seguridad gobiernan al sistema.**

# 13. ¿Necesitamos RAG?

Sí, pero no haremos un RAG complejo.

Para el PoC:

```text
aml_policies
      ↓
retrieval
      ↓
relevant policies
      ↓
LLM
```

Usaermos PostgreSQL y búsqueda simple.

No usar:

- Qdrant    
- embeddings    
- vector search    

No aportan suficiente valor al PoC.

---

# 14. ¿Necesitamos MCP?

> No necesriamente. Las tools están diseñadas como contratos independientes del modelo y podrían exponerse posteriormente mediante MCP para interoperabilidad con plataformas de agentes.

Si tenemos tiempo, podríamos incluso agregar una tool MCP como complemento, pero **no la pondría en el critical path**.

# 17. Una decisión importante: ¿microservices?

**No.**

Usar un **modular monolith**.

Algo como:

```text
backend/
├── api/
├── agent/
├── harness/
├── tools/
├── domain/
├── data/
├── policies/
└── evaluation/
```

¿Por qué?

Porque el problema no necesita distribución.

Y además:

> **Un sistema modular no necesita convertirse en microservices para ser escalable conceptualmente.**

 ¿Por qué no microservices?

> "Porque en esta etapa el problema dominante es validar el workflow y las propiedades de seguridad del agente, no resolver distribución.
